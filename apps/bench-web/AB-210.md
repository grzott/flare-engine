# #210 A/B: how `loadCanvasKit` hands canvaskit-wasm its wasm

This is an experiment branch for [#210](https://github.com/grzott/flare-engine/issues/210). It
holds a switch in `packages/render-web/src/loader.ts`, a page query parameter, and a runner that
captures all three arms interleaved into `results/ab-210.ndjson`. Every change is marked
`#210 A/B`. Do not merge the branch as it is. "If arm C wins" below describes the real fix PR.

## The arms

The canvaskit-wasm 0.42 glue never reads `wasmBinary` and has no `instantiateWasm` hook. It
always calls `WebAssembly.instantiateStreaming(fetch(locateFile()))`. Only the URL changes.

| Arm | `?wasmArm=` | What the loader does | The glue streams from |
|---|---|---|---|
| A | `blob` | Our progress download, then `locateFile` returns a `blob:` URL of those bytes. This is the current path, and also what you get when the global is unset. | `blob:` |
| B | `url` | No download of our own. `locateFile` returns the server URL, so the glue downloads once. Progress jumps straight to 1. | `http:` |
| C | `url-cached` | Our progress download (default `cache` mode), then `locateFile` returns the same server URL. This is the exact pre-#196 call. | `http:`, which the HTTP cache can serve |

## What decides whether arm C can work

- **The server can be cached.** `scripts/server.ts` sends `/canvaskit.wasm` with
  `Content-Type: application/wasm`, `Cache-Control: public, max-age=31536000, immutable`, and
  `Content-Length: 8242911`. It sends no `ETag` or `Last-Modified`, and none is needed inside an
  explicit `max-age`. It sends no compression and no `no-store`, so no header change was needed for
  any arm.
- **The lane's "cold" cannot cache the wasm.** `coldstart-driver.mjs` treats "cold" as a fresh
  `browser.newContext()`. It does not disable the cache, and Playwright disables it only when a
  route intercepts requests, which this driver never sets up. A fresh context is an off-the-record
  context with an in-memory HTTP cache. A probe on 2026-11-12, Chromium 156, fetched the same URL
  twice in one page:
  - the 8,242,911-byte wasm, in a `newContext()`: the server was hit twice;
  - a 4,000,000-byte body, in a `newContext()`: one server hit, then a cache hit;
  - the 8,242,911-byte wasm, in a fresh on-disk profile (`launchPersistentContext`): one server
    hit, then a cache hit.

  The results fit a per-entry size cap in the in-memory cache. They also explain the header note
  in `coldstart-driver.mjs` that "the disk cache does not engage". **In the lane's own cold start,
  arm C downloads twice, so `coldStart.cold4g` comes back at about 32.5 s.** Pre-#196 read 32.5 s
  for the same reason.
- **So the runner measures cold start twice per arm.** It runs once the way the lane runs it
  (comparable with `web-history.ndjson`), and once in a fresh, empty on-disk profile
  (`BENCH_WEB_COLDSTART_PROFILE=persistent`). The second run is a regular browser profile, where
  arm C's second fetch can come from the cache.
- **Every row records how the wasm arrived.** `wasmRequests` counts network downloads, HTTP-cache
  hits and `blob:` reads, all from CDP. `wasmArmTaken` is the path the loader reports it took. A row
  whose `wasmArmTaken` differs from its arm is logged as an error and left out of the table.

The table should show:

| Arm | wasm on the render page / lane cold4g | wasm, cold4g in a disk profile |
|---|---|---|
| `blob` | `net 1 + blob 1` | `net 1 + blob 1` |
| `url` | `net 1` | `net 1` |
| `url-cached` | `net 2` | `net 1 + cache 1` |

If `url-cached` shows `net 2` in the disk-profile column, the cache did not engage there either,
and arm C cannot keep cold4g near 16.7 s.

## Before you start

1. **Install the Playwright browser.** `playwright` is now 1.65.0 (#265, 2026-11-09). It wants
   `chromium_headless_shell-1254` (Chromium 158.0.8127.18), which is not installed on the
   workstation: only 1234 and 1248 are there. Run
   `node node_modules/playwright/cli.js install chromium`. This also changes the browser.
   The pre-#196 band (89.5-97.4 ms) and every window so far ran on Chromium 156 or earlier, so
   compare the arms with each other first and with the band second.
2. **Set the power plan to High performance.** Check it with `powercfg /getactivescheme`. If it is
   not, run `powercfg /setactive 8c5e7fda-e8bf-4a96-9a85-a6e23a8c635c`. The runner refuses Power
   saver and warns on Balanced.
3. **Keep the host quiet.** Close browsers, IDE indexers, RGB visualisers and other GPU or CPU
   loads. The runner refuses a host above 15% busy (override: `BENCH_WEB_ALLOW_BUSY=1`). It samples
   the load before every arm step and stores it on each row as `hostLoadPct`.
4. **Pin to the P-cores.** On a hybrid CPU the runner refuses to start unpinned and prints the
   command. It does not relaunch itself. Children inherit the mask, and each row records it as
   `affinityMask`, which should read `0xffff`.

## Commands, in order (repo root, Git Bash)

```sh
powercfg /getactivescheme
node node_modules/playwright/cli.js install chromium
cmd //c "start /affinity FFFF /b /wait bun run bench:web:ab210"
```

The root script runs through turbo, so `render-web`'s `dist/` is rebuilt with the switch before
the first capture. The bench page bundles `@flare-engine/render-web` from `dist/`. If you run the
package script directly (`apps/bench-web`, `bun run bench:web:ab210`), build first. Otherwise every
step fails with "the page loader wrote no `__FLARE_WASM_ARM_TAKEN`".

- `--rounds N` changes the number of rounds (default 3). Example:
  `cmd //c "start /affinity FFFF /b /wait bun run bench:web:ab210 --rounds 5"`.
- To reprint the table from the file without measuring:
  `cd apps/bench-web && bun scripts/ab-210.ts --report`.

**How long it takes:** 9 arm steps (3 rounds × 3 arms). Each step is one render-suite capture
(about 70 s), the lane's cold start (about 40 s, or 70 s for `url-cached` because it downloads
twice at 4G) and the disk-profile cold start (about 25 s). Expect about 25 minutes, plus about a
minute of turbo build. Allow 35.

A failed step writes an `error` row, and the run continues. The exit code is 1 if any step failed.
A second run appends to the same file, and `--report` aggregates everything in it. The header line
lists every commit, Chromium version and affinity mask it saw, so check it shows one of each.

## Reading the table

The first table has one row per arm. Each figure is the median across captures of that capture's
p50, with `[min-max]` beside it:

- `zone-bg path`, `outline effect` and `1000 sprites / 1 atlas`;
- `vs band`: `zone-bg path` against the pre-#196 band, 89.5-97.4 ms inclusive;
- `cold4g` and `cold`: the lane's own cold start.

The second table shows the wasm request patterns, the disk-profile cold start and the error count.

1. **Check provenance first.** You need one commit, one Chromium, affinity `0xffff` and High
   performance. Each arm needs `n` = 3 and 0 errors.
2. **Check the wasm columns** against the expected patterns above. A different pattern means the
   arm did not do what its name says. Then do not read its timings.
3. **Compare the arms with each other on `zone-bg path`.** A real effect separates the arms by more
   than each arm's own `[min-max]` spread.
   - **A above B and C, and B and C level:** the `blob:` source is the cost. The mechanism is the
     URL scheme and not the bytes.
   - **All three level:** the load path is not the cause. In the latest published window
     (`0b7ea242`, 2026-11-08, arm A), `zone-bg path` already read 96.5-97.1 ms, inside the band. The
     110 ms in the `980e8078` window may have been the machine and not the loader. Close #210 under
     its "no load path recovers the raster cost" clause, but with the finding that there was no
     cost to recover. State the numbers and the Chromium version.
4. **Read cold4g.** Arm A should read about 16.7 s in both columns. For arm C, use the
   disk-profile column: a real browser with a disk cache does not download twice.

## If arm C wins

Arm C wins if `zone-bg path` is back in the band and cold4g is about 16.7 s in the disk-profile
column.

The fix PR keeps arm C's behaviour and removes the switch. In practice that reverts #196's `blob:`
hand-off: the 0.41+ browser path becomes the progress download, then
`initFn({ locateFile: () => wasmUrl, wasmBinary })`. That PR has to settle three things, all owner
calls:

- **The lane's cold4g goes back to about 32.5 s.** The lane's `newContext()` cache cannot keep the
  wasm. Either move `coldstart-driver.mjs` to a fresh on-disk profile for good (`persistent` here,
  which breaks the series in `web-history.ndjson`, so say so in the PR), or accept the jump and
  explain it.
- **Private windows download twice.** A Chromium private window has the same in-memory cache, so
  arm C downloads the 8.2 MB wasm twice there. That is the trade-off to record in the `loader.ts`
  comment.
- **The single-download tests change.** The `loadCanvasKit single download` tests
  (`packages/render-web/tests/loader.test.ts`) assert a `blob:` URL and one network hit. Arm C
  cannot pass them as written, because a unit test has no HTTP cache. The arm C test on this branch
  shows the replacement shape: the server URL to the glue, progress reported, default cache mode.

It is a `patch` changeset, no ADR. A `render-web` change stales every web lane, so the PR names
the recapture the next release needs.

If arm B wins and C does not, the scheme is the cause, and the price is progress reporting. That
is an owner decision, not a fix.

## Cleanup

```sh
rm apps/bench-web/results/ab-210.ndjson
```

The file is gitignored (`apps/bench-web/.gitignore` ignores `results/`), so it cannot be committed
by accident. The runner never writes `web-history.ndjson`, a `*-latest.json` sidecar or a baseline.
`run.ts` refuses to capture while `BENCH_WEB_WASM_ARM` or `BENCH_WEB_COLDSTART_PROFILE` is set.
After the decision, strip every `#210 A/B` marker. Run `git grep -n "#210 A/B"`, then delete
`src/wasm-arm.ts`, `scripts/ab-210*.{ts,mjs}`, `tests/ab-210.test.ts`, this file, and the
`bench:web:ab210` entries in both `package.json` files and `turbo.json`.
